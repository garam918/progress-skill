# Tracker format and CLI

## Commands

Use `python3 -B <skill-dir>/scripts/progress.py --root <project-root>` before the subcommand. The default root is the working directory. Relative paths passed to `--plan` and `--checks` resolve from the working directory.

| Subcommand | Behavior |
| --- | --- |
| `init --plan FILE` | Create `.progress/tasks.json` from a plan. Fails if a tracker already exists. |
| `status [--json]` | Read the current snapshot. JSON includes `tracker`, `metrics`, and `next_action`. |
| `estimate` | Calculate implementation progress from a JSON assessment on stdin, as described in [quick-check.md](quick-check.md). |
| `set ID STATE --expect-version N [--implementation TEXT]... [--checks FILE] [--note TEXT]` | Replace a task's state, implementation evidence, checks, and note. `N` is the task's `version` from `status --json`. |
| `replan --plan FILE --expect-revision N` | Replace the full plan. `N` is `tracker.revision` from `status --json`. A task omitted from the replacement is removed from scope. |
| `report` | Save the current snapshot to `.progress/report.md` using [the report template](../assets/report.md). |
| `validate` | Check the existing tracker schema, task states, and dependency graph. |

Exit status `0` means success, `1` means an invalid input, version conflict or file operation failure, and `2` is a CLI usage error.

## Plan and evidence inputs

The plan has `project`, `scope`, and `tasks`. Each task requires `id`, `title`, `weight`, and a `criteria` object mapping criterion IDs to observable outcomes. `depends_on` is an optional array of other task IDs. IDs use lowercase ASCII letters, digits, and single hyphens. Task IDs must be unique, weights are positive integers, and dependencies must resolve without cycles. An empty plan reports unknown progress.

`init` seeds `todo` tasks. `replan` preserves status and evidence for the same ID with unchanged criteria and the same set of dependencies. A new task or a changed criterion or dependency set starts at `todo` with cleared evidence. Title or weight changes preserve evidence. Omitted tasks leave the denominator, and reusing a removed ID creates a new task. The workflow should account for behavior changes across tasks when revising scope.

`set` accepts any state in [the state table](repository-audit.md#record-what-you-observed) when the supplied evidence fits it. This allows direct transitions during an audit and backwards transitions on regression. Each update is a full snapshot, so repeat still-valid `--implementation` entries and include still-valid checks you want to retain. Omitted fields clear their previous values. `todo` accepts no evidence. `blocked` requires `--note`. `implemented` and `verified` both require one or more implementation entries.

`--checks` accepts a UTF-8 JSON array. Each item has `criterion`, `kind` (`automated` or `manual`), `result` (`passed` or `failed`), and `detail`. Use at most one item per criterion. `verified` requires a passing item for every criterion. The CLI validates the recorded structure and coverage. The caller runs or inspects the checks and judges whether the evidence applies.

## Stored snapshot and writes

- `.progress/tasks.json` stores the plan and each task's `state`, `version`, `implementation` array, `checks` array, and `note` string or `null`. The top-level `schema_version` is `1`. The first `revision` is `1`, and `updated_at` records the latest change in UTC.
- Each substantive update increments the tracker revision and assigns it as the version of changed tasks. A concurrent update to a different task can succeed with its original task version. A stale update to the same task or a stale full replan is rejected. After a conflict, compare the new snapshot with your intended change before retrying.
- Writers take a POSIX lock on `.progress/.lock` across the read, validation, and write. Each output file is flushed and atomically replaced from a temporary file in the same directory. The OS releases the lock when the process exits. Keep the lock file in place while either client can write. Use a shared local filesystem for both clients.
- `report.md` records its source revision. It is regenerated by `report`, and later state updates can make it older than `status`. Use the CLI to regenerate it. The files are local to the checkout, including when the project uses multiple Git worktrees.

## Metrics

Both rates use the sum of all task weights in the current plan. Implementation uses the weights of `implemented` and `verified` tasks. Verification uses the weights of `verified` tasks. `todo`, `in_progress`, and `blocked` contribute zero to both numerators. A blocked verification with intact implementation can be recorded as `implemented` with a note. Rates are truncated to one decimal place, so unfinished weight cannot display as `100.0%`. An absent or empty plan yields `null` in JSON and `Unknown` in Markdown.

The next-action suggestion follows plan order within each priority. It suggests continuing work in progress, then verifying implemented work, then starting an eligible `todo`, then resolving a blocker. Dependencies affect `todo` eligibility for this suggestion. Judge completion against the acceptance criteria.
